## 1. Personas in play

**Verified Student — Asker.** Junior undergraduate at the launch campus, identity-anxious about
placement/course/internship/professor questions specifically because their *assigned* senior knows
their name, face, and branch. Wants to ask the whole senior pool without being identifiable.
*(PRD §1 ICP, §3 Primary user.)*

**Verified Student — Answerer.** Senior/recent-batch student at the same campus, same account type
and identity model as the Asker — the supply side of the read-heavy Q&A archive, incentivized by
persistent pseudonymous reputation. *(PRD §3 Secondary user.)*

**Operator.** The founder — sole moderator/grievance-handler at launch, AI-first with human
escalation rather than a manual moderation team. Needs a working console to act on AI-escalated
content and grievance reports within SLA. *(PRD §3 Operator; TRD §4 Human Escalation Queue,
Grievance & Takedown Service; TRD API A9.)*

## 2. User Flows

*One flow per P0 (F1–F8), plus two supplementary flows required by TRD architecture decisions that
have real, non-optional UX consequences (F9: `offline_write_queue`, TRD §3; F10: the operator
console implied by components §4 and API A9). Steps are actor → action → system response → screen,
grounded in TRD `apis`.*

### F1 — College-Email Verification & Derived Year Badge
*Serves: `p0_requirements[R1]`. Screens: S1, S2, S3, S4.*

1. Prospective student enters college email on **S1**. Client validates format; calls **A1**
   `POST /verification/initiate`.
2. A1 succeeds → verification-pending confirmation. Screen moves to **S2** (check-your-email), with
   a resend affordance.
   *Branch:* A1 error (non-campus domain / already-used / malformed / rate-limited) → **S1** shows
   an inline error; user stays on S1.
3. Student retrieves the token/OTP from email, enters it on **S3**. Client calls **A2**
   `POST /verification/confirm`.
4. A2 succeeds → Identity Account activated, year badge derived, Pseudonymous Profile
   created/linked. **S4** shows the **success** state: pseudonym + derived year badge revealed, raw
   email never displayed — this is R1 acceptance criterion 1, satisfied verbatim.
   *Branch (R1 AC2):* A2 error — enrollment year cannot be reliably parsed → **S4** shows the
   **blocked** state: registration held / routed to manual-fallback queue, explicit copy that no
   year was guessed. This is a legitimate non-success terminal state, not a redesign target.
   *Branch (R5 tie-in):* A2 error — email matches an existing Ban Record (A11 internal check) →
   **S4** shows the **refused** state: registration permanently blocked; surfaces a link to S15
   (Grievance Officer Contact) for anyone who believes this is a mistake — no dispute API exists in
   the TRD for this case (see Open Question OQ-12).
   *Branch:* A2 error — token expired/invalid → **S4** shows an **error** state with a retry/resend
   path back to S2.
5. Success (step 4) lands the student on **S5** (Home Feed), now onboarded.

### F2 — Persistent Pseudonymous Identity
*Serves: `p0_requirements[R2]`. Screens: S4, S11 (display touchpoints: S5, S6, S7, S8).*

1. Verified student opens **S11** (My Profile) in any session, including a return visit days later.
   Client loads the same Pseudonymous Profile created in F1 — pseudonym, year badge, reputation
   score, status — unchanged across sessions.
2. **S11** success state shows the persistent pseudonym + badge + reputation, satisfying R2 AC2
   ("same pseudonym and its accrued reputation carry forward").
3. Whenever the student posts or answers (S6/S8), content is attributed to the persistent
   pseudonym + year badge everywhere it's displayed (S5, S7) — never to real identity, satisfying
   R2 AC1.
4. Success: identity is consistently pseudonym+badge everywhere; raw identity never surfaced
   (cross-checked against TRD NFR "identity non-disclosure").

### F3 — Anonymous Junior↔Senior Q&A Core (Ask & Answer)
*Serves: `p0_requirements[R3]`. Screens: S5, S6, S7, S8.*

1. Student with an information need taps **Ask** from **S5**, opens **S6**, selects a topic tag,
   writes title/body, submits. Client calls **A3** `POST /questions` with a client-generated local
   ID + idempotency key.
   *Branch (offline):* no connectivity → write queues locally as a Sync Queue Item instead of
   calling A3 directly; **S6** shows the `queued_offline` state (continues in F9).
2. A3 succeeds → question resource returned with `moderation_status` (`pending` | `published` |
   `blocked`). **S6** shows a success confirmation and routes to **S7**, which displays the
   question with its current status.
   *Branch errors:* banned/suspended profile → forbidden (shown on S6); empty/invalid topic →
   rejected (shown on S6); Moderation Gateway unavailable/timeout → question still created with
   `moderation_status = pending` (not an error per A3's own contract — see F6).
3. Another student browses **S5/S9/S10**, opens a published question on **S7**, writes an answer on
   **S8**. Client calls **A4** `POST /questions/{id}/answers` with the same client-ID/idempotency
   pattern.
4. A4 succeeds → answer resource with moderation status, threaded under the question on **S7**,
   attributed to the answerer's pseudonym + year badge (R3 AC2).
   *Branch errors:* same moderation/ban/idempotency errors as A3; parent question not found/removed
   → rejected (shown on S8).
5. Success: the question is published and answerable; the answer threads under it with pseudonym
   attribution — the flow's terminal success state.

### F4 — Search & Browse Across Batches
*Serves: `p0_requirements[R4]`. Screens: S5 (entry point), S9, S10.*

1. Student opens **S9** (Search), enters a keyword and/or topic/cohort filter. Client calls **A5**
   `GET /questions/search`. *Alt entry:* student opens **S10** (Topic Browse) and picks a topic
   with no keyword — same A5 contract, topic-only filter.
2. A5 returns matching published questions/answers across batches (not scoped to the searcher's own
   cohort) → **S9**/**S10** show a results list (R4 AC1).
   *Branch:* invalid query params → **S9** shows a rejected-input error.
   *Branch:* no matches → **S9** shows A5's explicit empty-state payload (not an error — R4 AC2)
   inviting the student to post a new question; deep-links to **S6**.
3. Success: relevant existing content is surfaced, or the user is gracefully invited to create new
   content when none exists.

### F5 — Reputation With Something to Lose + Permanent Ban Enforcement
*Serves: `p0_requirements[R5]`. Screens: S7 (voting), S11 (reputation display), S4 (ban-refusal
branch, shared with F1).*

1. Student reading an answer on **S7** taps upvote or accept-answer. Client calls **A6**
   `POST /answers/{id}/vote` or `/accept`.
   *Branch errors:* self-vote forbidden; duplicate vote forbidden; banned/suspended actor forbidden;
   target not found — shown inline on S7.
2. A6 succeeds → a server-authoritative Reputation Event is applied (append-only ledger, TRD §3/§5),
   updated reputation score returned. **S7** reflects the applied vote/accept; the content author's
   **S11** reflects the updated score next load. This satisfies R5 AC1.
3. Separately: a previously banned individual attempts to re-register with the same college email
   via F1. At A2 confirm, the A11 internal Ban Record lookup matches the hashed email →
   registration refused. **S4** shows the **refused** state (same branch as F1 step 4) — re-entry is
   permanently blocked regardless of whether the original account was deleted (R5 AC2; TRD NFR "ban
   durability").
4. Success: this flow has two legitimate terminal successes — visible reputation change on the
   positive path, and a durable refusal on the negative path. A refusal is not a failure of this
   flow; it is the point of R5.

### F6 — AI Moderation on Every UGC Submission
*Serves: `p0_requirements[R6]`. Screens: S6, S7, S8 (submission touchpoints), S12 (status list),
S16 (operator, supplementary — see F10).*

1. Every question/answer submitted via S6/S8 (or synced offline via F9) is synchronously routed
   through the Moderation Gateway → internal **A7** call to the External AI Moderation API before
   any publish decision (R6 AC1) — this happens for every UGC write, with no exceptions, including
   sync-time re-entry from A10.
2. A7 classifies `auto-pass` / `auto-block` / `escalate`.
   - **auto-pass:** `moderation_status` becomes `published` immediately; content is live on S7/S5.
   - **auto-block:** `moderation_status` becomes `blocked`; S7/S12 show a **blocked** state with a
     general policy-reason message, never published anywhere (R6 AC2).
   - **escalate:** `moderation_status` stays `pending`; content routes to the Human Escalation Queue
     (S16, operator) rather than auto-approving (R6 AC3); S7/S12 show a **pending — under review**
     state.
   - **external API timeout/outage:** fail-closed — `moderation_status` stays `pending`, retried
     with backoff; unresolved past a threshold auto-routes to S16 rather than publishing or
     dropping (A7's own error contract; NFR "moderation failure posture").
3. Operator reviews an escalated Moderation Case on **S16**, decides. Outcome updates
   `moderation_status` to `published`/`blocked` (see Open Question OQ-11 on the missing distinct API
   id for this action).
4. Success: 100% of published content has a cleared Moderation Case (NFR "moderation coverage"); the
   user always sees one of exactly three statuses — `pending` | `published` | `blocked` — never a
   silent bypass.

### F7 — IT Act Grievance Mechanism & Takedown
*Serves: `p0_requirements[R7]`. Screens: S13, S14, S15, S17 (operator, supplementary — see F10).*

1. Any user viewing content on **S7** taps Report, opens **S13**, selects a reason, optionally
   stays anonymous, submits. Client calls **A8** `POST /reports`.
   *Branch errors:* content not found → rejected; rate-limited abuse → throttled — shown on S13.
   *Branch:* duplicate report by the same actor on the same content → merged into the existing
   ticket, not rejected — S13 shows a **merged** state referencing the existing ticket ID.
2. A8 succeeds → grievance ticket ID + SLA-bound acknowledgement timestamp. **S13** shows success;
   if the reporter was not anonymous, the ticket also appears on their **S14** (My Reports) list
   (R7 AC1).
3. Operator reviews the queued Grievance Report on **S17**, decides takedown / dismiss /
   escalate-further, calls **A9** `POST /reports/{id}/resolve`.
   *Branch errors:* report not found; unauthorized (non-operator) caller forbidden.
   *Branch:* resolution lands past the SLA deadline → not blocked, but flagged/logged as an SLA
   breach (visible to the operator on S17; whether it's also surfaced to the reporter on S14 is an
   open question, OQ-13).
4. A9 succeeds → grievance status updated, audit-log entry written; if takedown, the underlying
   content's moderation status updates to `blocked` wherever it's shown (S7/S12). **S14** reflects
   the resolved status and action taken for the original reporter (R7 AC2).
5. **S15** (Grievance Officer Contact) is reachable from Profile/Settings at all times, independent
   of any specific report — satisfying R7 AC3 ("contact details are published and reachable" at
   launch, not conditioned on a report existing).
6. Success: every report reaches an acknowledged, SLA-timestamped, auditable resolution; contact
   info is always discoverable.

### F8 — Retention & Density Instrumentation (event-hook flow, no dedicated screens)
*Serves: `p0_requirements[R8]`. Screens: none — event hooks embedded in F1–F7's screens.*

1. Each meaningful user action (registration completed, first post/answer within week one, a WAU
   session ping, moderation auto-vs-escalated outcome, D30-cohort-relevant login) fires an
   Analytics Event via internal **A12** `POST /events`, riding on S1, S3, S4, S6, S7, S8, S9, S13,
   and session-start.
2. A12 acknowledges fire-and-forget; a malformed/rejected event is logged but **never** blocks or
   fails the primary user action it's attached to — this is itself part of A12's error contract, not
   a UX omission.
3. Success: every PRD §1/§5 metric (registration penetration, WAU density, D30 retention,
   activation, answer liquidity, auto-vs-escalated ratio) is computable purely from captured
   Analytics Events — satisfied structurally by hooks on other flows' screens, per TRD NFR "event
   instrumentation completeness." R8 legitimately needs no user-facing screen of its own.

### F9 (supplementary) — Offline Authoring & Sync Reconciliation
*Serves: `write_model[offline_write_queue]` (TRD §3), `p0_requirements[R6]` (moderation-on-sync
interaction). Screens: S6, S7, S8 (queue point), S12 (status view). Not a distinct P0 — required
because the TRD's write-model decision has documented, mandatory screen-state consequences (TRD §9
Risks: "a 'sent' question may sit invisible for a while after sync").*

1. Student loses connectivity mid-session, continues drafting/submitting on S6/S7/S8. Client queues
   the write locally as a Sync Queue Item (client-generated local ID + idempotency key) instead of
   calling A3/A4/A6 directly. Screen shows the `queued_offline` state — distinct from a normal
   loading spinner.
2. Connectivity returns. Client calls **A10** `POST /sync/batch` with all queued items. **S12**
   shows each item transition `queued` → `syncing`.
3. A10 returns a per-item terminal result:
   - `synced` (server-assigned ID) — the item re-enters the moderation gate per F6, so its
     user-visible status becomes `pending` next, **never** jumping straight to `published` (TRD §3,
     §9 Risk).
   - `conflict` — last-write-wins applied to the text field only (TRD §3); **S12** shows a
     "conflict resolved" note. Reputation/ban state is never touched by last-write-wins.
   - `rejected` — e.g. failed moderation or banned actor; **S12** shows `rejected` with the reason.
4. Success: 100% of queued items reach a terminal state — none silently lost (NFR "offline sync
   reliability") — and the student always has a truthful, current view of where each offline-authored
   item stands on S12.

### F10 (supplementary) — Operator Moderation & Grievance Console
*Serves: `p0_requirements[R6]`, `p0_requirements[R7]` (operator-side completion of both). Screens:
S16, S17. Not a distinct P0 — required because A9 is an operator-invoked API contract
("unauthorized caller (non-operator) → forbidden") and the Human Escalation Queue is explicitly
named in TRD §4 as "the single-founder operator's console."*

1. Operator opens **S16** (Escalation Queue), reviews AI-ambiguous/high-risk content flagged by
   A7's `escalate` tier, decides. *(See OQ-11 — no distinct API id in the TRD's 12 contracts covers
   this action separately from A9's report-scoped resolve; documented as a gap, not invented here.)*
2. Operator opens **S17** (Grievance Resolution), reviews a Grievance Report, calls **A9** to
   resolve (takedown / dismiss / escalate-further).
3. Success: every escalated Moderation Case and every Grievance Report reaches a decided, audited
   terminal state within the founder's real operating capacity — the same success condition F6/F7
   depend on from the operator side.

## 4. Screen Detail

*States marked with an asterisk (\*) are product-specific, beyond the mandatory four
(empty/loading/error/success); they exist because the TRD's own write model and moderation gate
make them real, not because of scope creep.*

### S1 — Email Entry
**Purpose:** collect a college email and initiate verification (A1).
**States:**
- empty — blank form, default on load.
- loading — submitting to A1.
- error — non-campus email domain refused / already-used-or-registered email refused / malformed
  email rejected / rate-limited (all from A1's error list).
- success — verification-pending confirmation; auto-navigates to S2.

**Primary action:** Submit email.
**data_needs:**
| Field | Mode | Trace |
|---|---|---|
| college email address | write | `apis[A1].inputs[college email address]` |
| domain-refusal error message | read | `apis[A1].errors[non-campus email domain refused]` |
| already-used error message | read | `apis[A1].errors[already-used/already-registered email refused]` |
| rate-limit error message | read | `apis[A1].errors[rate-limited]` |

### S2 — Verification Pending
**Purpose:** check-your-email acknowledgement with a resend affordance.
**States:**
- empty — n/a (screen only renders after S1 success); documented, not skipped.
- loading — resend request in flight.
- error — resend delivery failed (`[ASSUMPTION]` — TRD §8 names "user-visible resend affordance" on
  Email/OTP Delivery Provider failure but doesn't specify UI copy).
- success — resend confirmed / awaiting user action (open-ended wait state).

**Primary action:** Resend verification email.
**data_needs:**
| Field | Mode | Trace |
|---|---|---|
| verification-pending confirmation message | read | `apis[A1].outputs[verification-pending confirmation]` |
| resend cooldown timer | read | `NEW:F1.step2 — prevents resend abuse, not named by any TRD entity/API but implied by A1's rate-limiting error` |

### S3 — Confirm Token/OTP
**Purpose:** collect the verification token/OTP and call A2.
**States:**
- empty — blank input, default on load.
- loading — submitting to A2.
- error — token expired/invalid (`apis[A2].errors[token expired/invalid]`); loops back toward S2 for
  resend.
- success — A2 accepted; auto-navigates to S4 with the result (success/blocked/refused branch
  decided there).

**Primary action:** Submit token/OTP.
**data_needs:**
| Field | Mode | Trace |
|---|---|---|
| verification token/OTP | write | `apis[A2].inputs[verification token/OTP]` |

### S4 — Registration Outcome
**Purpose:** show the three PRD-mandated verification branches as distinct states.
**States:**
- empty — n/a (result-only screen; see S3 for pre-submission empty state).
- loading — awaiting A2 response.
- error — token expired/invalid, offering retry (shared with S3's error, surfaced here if reached
  directly).
- success — Identity Account activated; derived year badge + newly linked pseudonym shown; raw
  email never displayed (R1 AC1). Auto-navigates to S5.
- **blocked**\* — enrollment year could not be reliably parsed; registration held / routed to
  manual-fallback queue; explicit copy stating no year was guessed (R1 AC2;
  `apis[A2].errors[enrollment year cannot be reliably parsed...]`).
- **refused**\* — email matches an existing Ban Record; registration permanently blocked (R5 AC2;
  `apis[A2].errors[email matches an existing Ban Record → registration refused]`); links to S15.

**Primary action:** Continue to Home (success) / Resend or contact grievance officer (blocked,
refused).
**data_needs:**
| Field | Mode | Trace |
|---|---|---|
| derived year badge | read | `entities[Pseudonymous Profile].key_attributes[verified-year badge]`; `apis[A2].outputs[derived year badge]` |
| assigned pseudonym/handle | read | `entities[Pseudonymous Profile].key_attributes[persistent pseudonym/handle]`; `apis[A2].outputs[newly linked/created Pseudonymous Profile]` |
| raw email | never displayed | `entities[Identity Account].key_attributes[verified college email (minimized/hashed at rest — never displayed)]` — explicitly excluded per NFR "identity non-disclosure" |
| blocked-state copy (no guessed year) | read | `apis[A2].errors[enrollment year cannot be reliably parsed...]` |
| refused-state copy (ban match) | read | `apis[A2].errors[email matches an existing Ban Record]` |
| link to grievance contact | read | `NEW:F1.step4c — no dispute API exists; UX-level link to the standing S15 contact page, flagged OQ-12` |

**Primary action:** Submit.
**data_needs:**

### S7 — Question Detail / Thread
**Purpose:** read a question and its threaded answers; vote/accept; entry point to report and to
answer.

## 6. Design Directions

*2–3 directions for the human taste gate. No mockups, no colors, no fonts — direction, not
execution. None is selected here; selection is human-only.*

**D1 — Quiet Utility.** Adjectives: minimal, dense, no-nonsense, fast, utilitarian. Archetype:
"dense and functional like Stack Overflow or a well-run mailing list." Optimizes for speed of
in-and-out use during a class break, high information density on feed/search screens, and a visual
tone that signals *this is a serious, trustworthy record of real answers* — not a toy.

**D2 — Warm Anonymous Community.** Adjectives: approachable, reassuring, gentle, human, low-anxiety.
Archetype: "warm like a well-moderated Discord server, softened like Headspace." Optimizes for
lowering first-post activation friction for a shame-laden ask — copy and interaction tone around
moderation/reporting states (pending, blocked, escalated) especially need to read as protective, not
punitive, since the entire wedge is about lowering the emotional cost of asking.

**D3 — Confident Campus Brand.** Adjectives: bold, energetic, youth-culture, expressive, proud.
Archetype: "bold and shareable like BeReal or Fizz." Optimizes for viral, campus-native distribution
and status signaling (reputation, year badges as visible flair) — directly serving the
time-limited land-grab constraint (PRD §6: "speed to density is the operative constraint") by making
the product feel worth showing a friend.
